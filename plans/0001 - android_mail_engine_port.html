Core/Package.swift: actual target and NIO dependency graph

Android MailRepository exposes local actions including sendDemo and resetDemo. RoomMailRepository seeds demo messages on account creation. Room entities lack server UID/UIDVALIDITY and sync state. Manifest currently declares no INTERNET permission.

iOS IMAP integration tests cover login/list/select/status/fetch/mailbox actions/IDLE; SMTP tests include live send-to-self behavior. These must not run against personal accounts implicitly. MIME fixture resources are candidates for the golden corpus.

Proposed architecture and SwiftNIO replacement
Compose screens / ViewModels
  → domain use cases + MailRepository contracts
    → Room-backed repository (observable local source of truth)
      → SyncCoordinator / operation queue / outbox
        → MailStore (IMAP now; JMAP v2)
        → MailSubmission (SMTP now; JMAP v2)
        → MimeCodec + EmailAddress
          → chosen protocol engine / TLS transport
Account setup → Autoconfiguration + CredentialStore → adapters

Proposed Gradle modules: :core:account, :core:email-address, :core:mime, :core:imap, :core:smtp, :core:autoconfig; :data:local, :data:sync, :data:credentials; existing :app for UI/composition. Final module granularity belongs to T05. Protocol modules must not import Compose or Room entities.

Protocol wire identity stays separate from local UUIDs. For IMAP, use account/mailbox/UIDVALIDITY/UID; sequence numbers are transient. Separate message content from folder membership where provider semantics require it. Store pending mutations durably before network execution. The Room flow remains responsive while sync runs.

Proposed adapters use Kotlin suspend functions and Flow, typed failures, bounded I/O and account-scoped cancellation. Screen navigation must not accidentally close an account session. JMAP remains a future adapter; no implementation work in this initiative.

Engine options and decision criteria

Candidate A · Existing Thunderbird Android components

Assess extraction/adaptation of existing IMAP, SMTP and MIME components behind our own interfaces. Potential reuse is attractive, but dependency graph, API stability, notices and maintenance need a spike.

Official repository

Local candidate checkout: ../thunderbird-android; mail/protocols/imap, mail/protocols/smtp, mail/common. No changes made there.

Candidate B · Eclipse Angus Mail

Provides Jakarta Mail implementation and protocol providers; Android guidance exists. Evaluate real Android build/runtime, TLS/auth, cancellation of blocking calls, IMAP feature access, MIME streaming and dependency footprint.

Official Android guidance · Project documentation

Candidate C · Netty or JVM sockets with a custom engine

Netty offers asynchronous transport and a channel/pipeline model similar in shape to SwiftNIO. It does not replace the iOS NIOIMAP parser/state integration automatically. A custom engine adds protocol, TLS, parser and resource-lifecycle maintenance.

Official Netty documentation

Provisional recommendation: keep iOS-like contracts and module responsibilities, compare A and B first, and choose C only if the measured gaps warrant owning a protocol engine. The module/adapter approach is approved; the specific library choice is still pending the spike. Pin versions after the spike; do not copy the iOS manifest’s moving main-branch dependency policy.
