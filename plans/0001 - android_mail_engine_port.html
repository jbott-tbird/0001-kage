Details, engineering standards and source evidence

Engineering principles and test strategy

SOLID: keep protocol transport/codec, MIME, domain policy, persistence and screen state focused. Depend on narrow interfaces at real boundaries; adapters must honor the same behavior and error contracts. Third-party/Room types do not leak into core domain objects.

KISS: prefer explicit state transitions, straightforward composition and small modules. Add an abstraction only for a demonstrated boundary, repeated policy or concrete variation. Do not build a generic engine framework to anticipate speculative protocols.

DRY: centralize shared validation, mapping policy and serialization rules with tests. Preserve distinct wire, domain and database representations where their responsibilities differ; mapping between them is intentional, not duplication to erase.

M1 verification: unit tests for models, MIME parse/serialize and error/codec behavior; deterministic transcripts and controlled local servers for IMAP/SMTP lifecycle, fragmented data, authentication, TLS/STARTTLS, timeouts and failure cases. Test cancellation and resource cleanup. Emulator smoke/integration tests verify Android runtime compatibility. No Compose/Room coupling needed.

M2 verification: unit tests for mapping and repository policies; real Room instrumentation tests for schema migration, identity, transactions, restart and isolation; controlled-server integration through repository adapters.

M3 verification: Compose UI and emulator end-to-end tests for setup, folder selection, refresh, reader/RTL, search, attachments, draft editing, send failures and retry. Keep all feasible integration/regression checks in emulator phases; P6 contains only provider/physical checks that need that environment. Passing unit tests is necessary evidence, not proof of every real-world behavior.

Automated tests must assert observable outcomes and realistic error cases. CI gates use repeatable fixtures without external credentials; known failures remain open in their originating phase. No arbitrary coverage percentage substitutes for the operation/behavior matrix.

Engine options and decision criteria

Candidate A · Existing Thunderbird Android components

Assess extraction/adaptation of existing IMAP, SMTP and MIME components behind our own interfaces. Potential reuse is attractive, but dependency graph, API stability, notices and maintenance need a spike.

Official repository

Local candidate checkout: ../thunderbird-android; mail/protocols/imap, mail/protocols/smtp, mail/common. No changes made there.

Candidate B · Eclipse Angus Mail

Provides Jakarta Mail implementation and protocol providers; Android guidance exists. Evaluate real Android build/runtime, TLS/auth, cancellation of blocking calls, IMAP feature access, MIME streaming and dependency footprint.

Official Android guidance · Project documentation

Candidate C · Netty or JVM sockets with a custom engine

Netty offers asynchronous transport and a channel/pipeline model similar in shape to SwiftNIO. It does not replace the iOS NIOIMAP parser/state integration automatically. A custom engine adds protocol, TLS, parser and resource-lifecycle maintenance.

Official Netty documentation

Both candidates built and passed bounded Android API30 tests; Angus is selected because the existing adapter has broader success/failure coverage, a smaller dependency graph and fewer application-level setup requirements. A custom Netty engine is not justified by the measured requirements.
