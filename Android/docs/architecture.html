Architecture in one minute

iOS: SwiftUI views use observable Account, Folder, Mailbox and Email managers from Swift packages. Account objects select an IMAP or JMAP client; protocol and MIME packages sit below those managers. The checked-out inbox and compose UI still contain sample data and placeholder actions.

Android: Compose screens collect state from MailViewModel. Domain models and repository interfaces separate screens from Room persistence and Angus-backed IMAP/SMTP/MIME adapters. Room owns cached mail and durable work; credentials live separately in Android Keystore storage.

Start at KageApp.kt for routes, AppContainer.kt for wiring, and CoreRoomMapper.kt for wire-to-database conversion. Android models retain iOS concepts, but an Android Account fixes one IMAP incoming and one SMTP outgoing server rather than iOS's general server list.

4 · Other areas and deliberate gaps

  • Managers and persistence. iOS AccountManager, FolderManager and EmailManager are not copied as manager classes. Android uses RoomMailRepository, RemoteMailRepository, Room Flow and the ViewModel.
  • Credentials and OAuth. iOS uses Keychain and OAuthButton; Android uses AndroidCredentialStore and GooglePlayAuthorization. A debug Android client ID is configured; the SDK build, emulator and live Gmail checks remain open.
  • Android-only durability. pending_operations, outbox, sync_cursors and history_cursors make actions, sending and backfill restartable. data/background adds optional Android scheduling and generic notifications. These have no direct counterpart in the captured iOS UI baseline.
  • Android support modules. :core:transport controls sockets; :core:demo supplies an offline adapter; :core:testkit and :core:integration hold protocol fixtures and cross-module tests.
  • Presentation gaps. iOS's rich HTML compose toolbar and broad Localization/*.lproj resources are not mirrored by Android's plain-text compose UI and English-only strings. iOS's feature-flag debug screen has no direct Android equivalent.

First steps for a cross-platform change

  1. Find the iOS view or core declaration above, then follow its Android screen → ViewModel → repository → model/adapter path.
  2. Check ios-parity.json for field and public-operation mappings, and the current port plan for acceptance and open gates. The ledger is a baseline inventory; verify present source before trusting a pending status.
  3. Use Android build and test commands and the relevant module tests. The newest Android changes still need an actual build, emulator run, and live Gmail/device checks; source presence or direct Kotlin compilation alone does not establish parity.
